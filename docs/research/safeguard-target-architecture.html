SafeGuard target architecture

Proposed end-to-end architecture. One stateful Agent Controller decides which evidence to check. Detection assesses risk at the current observation boundary. Warning Policy converts that assessment into a partner-facing action.

System overview

Partner API, Ingress, and Adapter
Apply access and input limits, preserve ordering, and convert source events into the common message format. Gateway receives native events. Norm preserves the source identity and maps message parts. The file-ingress path stores originals by reference.
Memory
Conversation Status stores the observed prefix, derived evidence, analysis, and warning history in separate namespaces. Original Assets retains the uploaded bytes and their identities. Both live in SafeGuard's service boundary.
Detection and Warning Policy
Detection produces an assessment for the permitted prefix. Warning Policy reads the committed result and its own warning history. The Partner API returns the warning action and the application presents its source references.

Detection and the agent loop

  1. At each eligible observation, bind the exact permitted prefix and its scoped state. Treat a stored assessment as an earlier judgment with its own evidence and version.
  2. Identify the uncertainties that could change the result. Choose among allowed lookups, content readers, and checks. Return each observation with its source and processing status. Keep sender claims, extracted observations, and verified facts distinct.
  3. Use a compatible model for each decision. Jev is a candidate to choose a verdict or action from allowed options. An approved LLM or specialist can interpret an input or perform open-ended analysis when that capability is needed. A Jev-based assessment can assemble its explanation from typed reasons and validated source references.
  4. Return the verdict and references when the evidence supports it. Return insufficient evidence for a material unresolved question. Preserve a separate outcome for execution failure. The Host validates the result. DetectionService commits the assessment against the bound version before Warning Policy acts.

Source links identify where evidence came from. Semantic support still needs an evaluation of whether those sources justify the assessment. Jev's role remains conditional on an equal-evidence comparison. Model evidence and selection criteria

Data boundaries, reliability, and evaluation

Scoped data access

Keep conversation state and originals within permitted account and conversation scope. Limit provider inputs to the authorized portions needed for a check. Carry forward the demo's incoming-only model boundary unless the source permissions and owner policy change.

Versioned processing

Preserve per-conversation order. Isolate scale-out work by conversation. Use stable event identities and reject stale commits. Reuse tool results only under the same source, processor version, and access scope.

Separate evaluation

Record versions, model and tool calls, failures, and latency. Keep evaluation labels outside live Detection. Compare warning quality and timing, evidence support, uncertainty, and resource use.

Open product decisions include partner authentication and delivery, retention and deletion policies, provider data permissions, operating limits, and when additional evidence should revise an active warning.
